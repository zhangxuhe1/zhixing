# 地点库省市级联筛选 + 关键字搜索 设计

## 背景与目标

管理端「地点库」(/places) 随录入增长,现有的单一层级下拉不足以支撑日常维护——运营需要"看某省某市下都录了哪些点位、缺什么"。目标:省→市级联筛选圈定子树范围,叠加名称关键字定位具体点位,减少翻表格的维护成本。

## 方案取舍

- **纯前端级联下拉(选定)**:页面本就一次性拉全量地点,树关系已在内存;建 children 索引 + 子树收集即可,零 API 改动。几百到数千地点量级毫无压力。
- 树形展开表格:改动大、"看某市全部点位"要逐级展开,维护效率反而低,弃。
- 服务端查询参数:当前数据量属过度设计,地点上万再议。

## 交互与语义

筛选栏一行:`[省 ▾] [市 ▾] [层级 ▾(现有)] [关键字输入框] [新建地点(现有)]`。

- 省下拉:全部 `level=PROVINCE` 节点(直辖市/特区如北京市、香港天然在列),按中文名排序。
- 市下拉:所选省的**直接子节点**中 `level=CITY` 者,按中文名排序;未选省时禁用;换省自动清空已选市。直辖市无市级子节点,市下拉仅"全部市"。
- 表格 = 最深已选节点的**整棵子树(含自身)** ∩ 层级筛选 ∩ 名称包含关键字(trim 后 includes),三者 AND。含自身是为了选中某市时还能顺手编辑该市节点行。
- 标题计数沿用现有 `shown.length`,自动显示过滤后数量。

## 实现要点

仅改 `apps/admin/app/places/page.tsx`:

- `useMemo` 建 `childrenByParent: Map<parentId, PlaceRow[]>`;
- 子树收集从 `cityId || provinceId` 出发迭代 BFS,`Set` 去重兼防脏数据成环;
- 过滤链替换现有 `shown` 计算;无新错误路径(纯内存过滤)。

## 验证

admin 无测试基建:`next build` 类型检查 + 人工走查(选省→选市→子树正确;直辖市;关键字与层级叠加;换省清市)。
