## 1. 结论摘要

本次审查发现 **1 个 P0 问题**：已认证普通用户可以利用照片上传链路的账号级配额缺失、照片上限并发竞态和整文件内存缓冲，持续灌入照片耗尽 VPS 共享磁盘（主路径）或撑高 API 进程内存（次路径），进而造成全站不可用并威胁 PostgreSQL、MinIO 数据可靠性。

除此之外，发现 3 个建议紧接处理的 P1：

1. 公开足迹审核在"管理员查看队列 → 点击批准"之间没有版本锁：用户于此人类时间窗内改动内容仍保持 `PENDING`，管理员会把从未看过的最新内容批准公开——这是对人工审核门的绕过，而非毫秒级竞态。
2. Apple 用户可在再次登录时直接替换昵称；公开故事实时读取 `User.nickname`，已通过审核的全部足迹会立即展示未经审核的新昵称。
3. 当前生产备份只包含 PostgreSQL，没有真正备份用户照片。

生产启动守卫没有禁止 `ZHIXING_DEV_AUTH=1` 一项，因触发条件是运维主动误配（非攻击者可触发），已由原 P1 下调并归入第 6 节纵深加固。

本轮没有发现第二个满足 P0 门槛的问题。依赖审计中也没有 Critical 或 High 等级漏洞。

## 2. P0 判定标准

本报告将下列问题定义为 P0：

- 可由公网攻击者或低权限普通账号稳定触发；
- 可造成全站不可用、大范围越权、核心私密数据泄露或不可恢复的数据损坏；
- 不依赖管理员主动配合、复杂供应链前置条件或仅存在于本地开发环境；
- 需要立即阻断或修复，不能等待常规版本迭代。

P1 表示高优先级安全或可靠性问题，但其触发条件、影响范围或可利用稳定性尚未达到上述 P0 标准。

## 4. P0：普通账号可通过照片上传耗尽全站资源

### 4.1 相关代码

- 全局限流与 15MB multipart 上限：[`apps/api/src/app.ts`](../../apps/api/src/app.ts#L68-L76)
- 照片数量检查、整文件缓冲及对象写入：[`apps/api/src/routes/photos.ts`](../../apps/api/src/routes/photos.ts#L46-L112)
- 无账号级数量配额的足迹创建：[`apps/api/src/routes/footprints.ts`](../../apps/api/src/routes/footprints.ts#L70-L89)
- API、MinIO 和 PostgreSQL 的同机部署：[`compose.prod.yml`](../../compose.prod.yml#L17-L68)
- 2C4G 起步部署规格：[`docs/deploy.md`](../deploy.md#L3-L6)

### 4.2 根因

照片上传链路包含以下相互叠加的问题：

1. **照片上限不是原子约束。** 接口先读取当前照片数量，再创建新记录。多个并发请求可以同时看到相同计数并全部通过检查。代码注释也明确接受了该竞态。
2. **每个上传都会整文件进入内存。** `await data.toBuffer()` 会将最大 15MB 的文件完整读入进程内存；该缓冲是 Node.js 堆外 `Buffer`（计入进程 RSS 而非 V8 堆），峰值取决于**同时在飞的上传并发数 × ≤15MB**，而非每分钟请求总量。
3. **上传频率过于宽松，且限流桶键不稳定。** 全局限流允许同一 Authorization 桶 300 次/分钟，没有更严格的照片专用限流或并发限制；更糟的是桶键使用完整 Authorization 头文本，而每次登录都会签发一枚新的会话 JWT，同一账号反复登录即可获得多个独立限流桶，进一步削弱按账号的频率约束。
4. **没有账号级存储配额。** 普通用户可以持续创建足迹并上传照片，没有累计照片数、累计字节数或每日上传量上限。
5. **对象存储先于数据库提交。** `storage.put` 成功后才执行数据库事务；数据库写入失败时，没有补偿删除，可能留下无法通过数据库追踪的孤儿对象。
6. **故障域没有隔离。** API、MinIO 和 PostgreSQL 默认部署在同一 VPS。API OOM 或磁盘打满可能同时影响所有核心服务。

### 4.3 受控复现结果

在本地测试数据库和测试 Bucket 中创建一个普通用户足迹，然后同时发起 30 个小图片上传请求：

```json
{
  "statuses": { "201": 30 },
  "photoRows": 30
}
```

预期上限为 12 张，实际 30 个请求全部成功，证明数量保护可以被并发稳定绕过。复现结束后已清理临时足迹、对象和数据库记录；最终测试库 `FootprintPhoto` 数量为 0。

本次没有向生产环境执行大文件或洪泛测试。资源耗尽影响由以下证据共同确认，其中**磁盘耗尽是更确定的主路径，内存压力为次要路径**：

- **磁盘（主）**：账号级字节配额缺失、建足迹数量不设上限，普通账号可持续创建足迹并上传照片，对象在 MinIO 卷里无界累积；对象存储与数据库共享同一宿主磁盘（部署文档建议 2C4G 起步），卷写满后同机 PostgreSQL 无法写 WAL、提交事务，直接波及全站；
- **内存（次）**：单请求最大 15MB 且代码 `toBuffer()` 完整缓冲，峰值内存 ≈ 同时在飞的上传并发数 × ≤15MB；300 次/分钟是**吞吐**约束而非并发约束，不能直接换算成"约 4.5GB 同时驻留内存"，要触发 OOM 需要制造足够高的**并发在飞**上传，可行但不由每分钟速率直接决定；
- 实际并发请求能够同时进入上传路径，且照片上限非原子约束（受控复现已证 30 并发绕过 12 张上限）。

### 4.4 影响

- MinIO 持久卷被持续上传或孤儿对象填满（主路径，不依赖高并发，持续灌入即可达成）；
- 同机 PostgreSQL 因磁盘耗尽无法提交事务或启动；
- 在足够高的并发在飞上传下，Node.js 进程因堆外 Buffer 内存压力被 OOM Kill（次路径，取决于并发度而非每分钟速率）；
- 所有用户无法登录、浏览内容、查看私密足迹或上传照片；
- 极端情况下出现数据库或对象存储恢复困难。

攻击者只需要一个普通 Apple 或邮箱登录账号，不需要管理员权限，因此该问题定级为 P0。

### 4.5 修复要求

建议按以下顺序处理：

1. 给照片上传增加独立的低频率限制和服务端并发上限；上传专用限流同时使用稳定的 `userId` 桶和真实 IP 桶，全局限流使用 IP 桶，任何桶都不能使用完整 Authorization 文本。
2. 增加账号级累计照片数、累计存储字节数、每日上传量和单文件大小配额。
3. 使用数据库锁和持久化上传预约记录，在读取 multipart 文件流前原子占用照片槽位、当日输入预算和累计存储预算；不能以提交期统计或单进程内存计数替代。
4. 将 `toBuffer()` 改为带严格上限和背压的流式上传，避免整文件驻留 API 内存。
5. 对象写入唯一、不可变的最终 key；数据库事务提交成功后完成账本。任何失败路径都必须补偿删除，补偿失败由账本驱动的 GC 重试；不强制 staging+复制。
6. 增加账本可解释范围内的孤儿对象扫描、MinIO incomplete multipart 生命周期规则、磁盘水位告警和服务资源限制。

### 4.6 P0 验收标准

- 100 个并发上传请求后，单足迹照片记录始终不超过 `FOOTPRINT_PHOTO_LIMIT`；
- 已满的照片槽位，以及依据“当前已用 + 活动预约 + 本次最坏预算”可判定会超出的账号额度，必须在调用 `req.file()` 前被拒绝；实际输入字节、输出字节、像素数超限则在有界流式处理中尽早中止；
- 同一用户无法通过创建多个足迹绕过账号级字节配额；
- API 在并发上传最大允许文件时，内存占用保持在明确的安全上限；
- 任意数据库失败、客户端断开和对象存储超时后均不遗留永久孤儿对象；
- 有自动化测试覆盖并发上限、配额竞争、上传失败补偿和对象清理。

## 5. P1 问题

### 5.1 审核操作可能批准管理员从未看过的最新修改（绕过人工审核门）

相关代码：

- 审核状态检查与无条件更新：[`apps/api/src/routes/adminReview.ts`](../../apps/api/src/routes/adminReview.ts#L53-L68)
- 用户修改公开内容后重新进入审核：[`apps/api/src/routes/footprints.ts`](../../apps/api/src/routes/footprints.ts#L92-L138)
- 公开足迹新增照片后重新进入审核：[`apps/api/src/routes/photos.ts`](../../apps/api/src/routes/photos.ts#L83-L112)

审核接口先查询足迹是否为 `PENDING`，然后使用仅包含 `id` 的条件执行 `update`（不带 `reviewStatus` 或内容版本判据）。真正的可利用窗口不是 handler 内两个 `await` 之间的毫秒级间隙，而是**管理员在 `GET /admin/review-queue` 看到内容、到点击批准之间的人类思考时间（秒级）**：用户在此期间改文本/日期或新增照片，`PATCH`/照片上传分支会把足迹**保持在 `PENDING`** 并刷新 `publicRequestedAt`（内容已变但仍留在队列里），管理员随后的 `approve` 复检 `PENDING` 通过，于是把**从未看过的最新内容**批准为公开。这是对"公开内容人工审核"这一核心安全模型的绕过，可利用性高于毫秒级竞态。

建议：为可审核内容增加 revision/version 或内容摘要；管理员必须审批明确版本，并使用 `updateMany where { id, reviewStatus: PENDING, revision: reviewedRevision }` 一类的条件更新。受影响行数不是 1 时返回 409，要求重新审核。

### 5.2 昵称可以在足迹审核通过后被替换

相关代码：

- 已存在身份再次登录时直接更新昵称：[`apps/api/src/routes/auth.ts`](../../apps/api/src/routes/auth.ts#L28-L45)
- 公开故事实时读取当前 `User.nickname`：[`apps/api/src/routes/public.ts`](../../apps/api/src/routes/public.ts#L13-L44)
- 审核队列展示的也是当前昵称：[`apps/api/src/routes/adminReview.ts`](../../apps/api/src/routes/adminReview.ts#L13-L45)

`POST /auth/apple` 接受客户端提供的 `nickname`。同一 Apple 身份再次登录时，`loginByIdentity` 会直接更新 `User.nickname`；已审核公开足迹没有昵称快照，公开 DTO 每次查询都读取当前 `User.nickname`。因此用户可以先让足迹和昵称通过人工审核，再以同一有效 Apple 身份令牌提交一个新的、未经审核的昵称，全部已公开足迹会立即展示它。

当前仓库没有已实现的昵称机审或独立昵称审核状态；产品规格中的内容安全机审属于公开上线前的后续规划，不能当作现有防线。

建议：短期禁止登录流程修改已存在用户的昵称；若产品需要可编辑昵称，则增加独立的昵称 revision、审核状态与已审核展示值，公共 DTO 只返回已审核昵称（未通过时使用安全默认值）。昵称是用户级内容，不应通过批量重审其全部足迹来间接处理。

### 5.3 用户照片没有纳入生产备份

当前 [`scripts/backup.sh`](../../scripts/backup.sh#L1-L8) 仅执行 `pg_dump`。[`docs/deploy.md`](../deploy.md#L56-L60) 也明确将 MinIO 卷备份列为未完成项。

这不是可由远程用户直接触发的代码执行漏洞，因此不定为 P0；但上线承载真实足迹照片前应视为发布阻断项。需要为 MinIO 配置独立、异地、周期性的对象备份或复制，并实际演练数据库与对象的一致性恢复。

## 6. 其他安全加固项

以下问题定级为纵深加固（含一项由原 P1 下调），建议纳入后续安全迭代：

- **生产启动守卫没有禁止开发登录旁路（原 P1，因触发条件为运维误配、非攻击者可触发而下调至此）。** [`apps/api/src/prodGuard.ts`](../../apps/api/src/prodGuard.ts#L19-L27) 只验证 SESSION、ADMIN、S3 三个密钥，没有在 `NODE_ENV=production` 时拒绝 `ZHIXING_DEV_AUTH=1`。这不是攻击者可触发的漏洞：`config.devAuth` 默认关闭，`compose.prod.yml` 未注入该变量，线上只读探测中 `POST /auth/dev` 返回 404；只有运维主动误设 `=1` 才会打开开发登录旁路。属纯纵深加固，但误配后果严重（认证旁路）、修复成本极低。建议：生产环境检测到 `ZHIXING_DEV_AUTH=1` 即拒绝启动，`compose.prod.yml` 显式注入 `ZHIXING_DEV_AUTH: ${ZHIXING_DEV_AUTH:-0}` 消除隐式状态，并补启动守卫测试。
- 本地 [`docker-compose.yml`](../../docker-compose.yml#L1-L22) 将 PostgreSQL 和 MinIO 绑定到所有宿主网络接口，并使用已知默认凭据。在不可信局域网运行时可能暴露开发数据，应改绑 `127.0.0.1`。
- API CORS 当前使用 `origin: true`，建议生产环境改为明确允许 iOS 所需接口和管理端域名。
- Admin Token 存储于 `localStorage`，管理端又动态加载第三方高德脚本；应补充严格 CSP，并评估改用 HttpOnly、Secure、SameSite 管理会话。
- 用户会话 JWT 有效期较长且无服务端撤销机制；账号安全事件发生后无法立即撤销已泄漏令牌。
- 应对照片进行服务端真实格式解码、尺寸/像素上限检查和统一重编码，不能仅信任 multipart MIME。

## 7. 已确认正确的关键安全实现

本轮未发现以下边界存在系统性缺失：

- 所有管理端 API 均使用 `requireAdmin`；
- 私密用户数据接口均要求 `requireUser` 并检查资源所有者；
- 公共足迹读取统一使用 `PUBLICLY_VISIBLE`，要求 `PUBLIC + APPROVED`；
- 公共 DTO 显式组装字段，没有直接返回含 `userId`、精确经纬度、精确拍摄时间或身份 subject 的 Prisma 实体；
- 私密照片读取同时支持所有者和已审核公开足迹，其他用户无法读取；
- iOS 会话令牌保存在 Keychain；无 Team 的 ad-hoc Catalyst 因缺 entitlement 临时使用 0600 Application Support 文件，取得正式签名后自动迁回 Keychain；照片上传前由客户端重编码以去除常规 EXIF；
- 生产 Compose 不公开 PostgreSQL 端口，API 和 MinIO 仅绑定宿主 `127.0.0.1`；
- 生产启动会拒绝空串、占位符和已知开发默认密钥；
- 当前线上开发登录关闭，S3 Bucket 不允许匿名列表或读取。

本轮为降级会话文件增加失败关闭与协调策略：当 Keychain 已持有当前 token、但旧降级文件删除失败时，必须将降级文件同步为同一 token。删除与同步都失败时：

- **内容已一致**（降级侧已是当前 token）：允许继续，并在日志中记录，下次启动再试清理；
- **内容仍不一致**：当前调用上抛，不能把双存储不一致静默当作成功。

成功同步后的读取/保存路径回归用例会再模拟「主存储后来不可用」，断言不会恢复出同步前的旧账号。双失败且内容不一致的用例则显式记录**已知残留**：本次 fail-closed 后旧文件仍可能留在磁盘，主存储再次不可用时仍可能读到旧账号，只能靠后续一次成功的删除/同步消除。迁移路径在 `primary.save` 成功后对 `reconcileFallback` 错误与主路径一致地上抛（同源 token 且内容一致时按上条放行）。由于本轮实现仅涉及 iOS 会话存储、对应测试和本报告，未重跑 `packages/db`、`apps/api`、`apps/pipeline` 与 Admin；这些组件的结果仍仅以上一节的历史基线为准。
